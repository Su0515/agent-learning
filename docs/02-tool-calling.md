# 02 工具调用（Tool Calling）

工具是 Agent 唯一能影响外部世界的方式，也是 Agent 能力的天花板。

## 一次工具调用的完整链路

```
1. 请求带上 tools 定义（JSON Schema）
2. 模型返回 tool_calls（函数名 + JSON 参数），不返回正文
3. 你的代码解析参数、执行函数
4. 结果以 role=tool + tool_call_id 回填到 messages
5. 再次请求，模型基于结果继续
```

注意：**模型从不执行函数**，它只是输出「我要调用谁、参数是什么」。执行永远在你的代码里，所以权限控制也在你手里。

## 工具定义的写法

```python
{
    "type": "function",
    "function": {
        "name": "search_docs",
        "description": "在项目文档中按关键词检索。返回最相关的前 5 段及文件路径。",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "检索关键词，用空格分隔"},
                "top_k": {"type": "integer", "description": "返回条数，默认 5，最大 20"}
            },
            "required": ["query"]
        }
    }
}
```

### 描述怎么写才好用

| 反例 | 正例 |
|------|------|
| `"description": "搜索"` | 写清**做什么、什么时候用、返回什么、边界在哪** |
| 参数名叫 `q` | 叫 `query`、`file_path` 这种自解释的名字 |
| 不给默认值 | 在 description 里写明默认值和取值上限 |

经验法则：把 description 当成给一个**聪明但完全不懂你系统的外包同事**写的接口文档。

## 工具设计原则

1. **少而精**。工具越多，选错概率越高、token 越贵。超过 20 个就该做分组或检索式加载。
2. **原子化**。`search_and_summarize_and_write` 这种复合工具没法复用，也没法观察中间结果。
3. **失败要可读**。返回 `"ERROR: 文件不存在: /a/b.md"`，而不是抛异常或返回空字符串。
4. **结果要对模型友好**。JSON 里塞一堆用不上的字段等于浪费上下文；长文本做截断并注明「已截断」。
5. **有副作用的工具要幂等或可确认**。删文件、发邮件、下单，前面必须有人工确认或 dry-run。

## 并行调用

支持并行工具调用的模型，会在一轮里返回多个 `tool_calls`。你应当并发执行它们（只读工具尤其），再把每个结果分别回填——每个都要带上对应的 `tool_call_id`，缺一个模型就会报错。

## 踩坑记录

- **参数校验缺失**：模型会给不存在的参数名，或把数字写成字符串。执行前统一做一遍 schema 校验。
- **工具结果太长撑爆上下文**：这是最常见的事故来源。给每个工具设返回上限。
- **模型反复调同一个工具**：多半是上次结果里没有它想要的信息，检查结果内容而不是加大 `max_steps`。
- **工具名重名或语义重叠**：`read_file` 和 `cat_file` 同时存在，模型会随机选。

## 动手练习

1. 给示例加一个 `http_get` 工具，把 URL 抓回来正文前 2000 字符。
2. 故意给两个语义重叠的工具，观察模型怎么选、日志里有什么迹象。
3. 把某个工具改成返回超长文本，看上下文和成本怎么变。
