# 04 编排模式

同样是「模型 + 工具 + 循环」，编排方式不同，能力和成本差一个量级。

## 1. ReAct（推理-行动交替）

最经典，也是默认选项。模型每轮输出「思考 → 动作 → 观察」，直到给出答案。

```
Thought: 需要先查当前目录
Action: list_dir(".")
Observation: a.py, b.md
Thought: 找到了 b.md，读它
Action: read_file("b.md")
...
Final: ...
```

优点：通用、易实现。缺点：步数多了会跑偏，且每轮都要完整上下文，贵。

## 2. Plan-and-Execute（先规划再执行）

先让模型产出任务清单，再逐条执行，执行完再决定是否重新规划。

适合：步骤明确的长任务（重构、数据迁移、写多章节文档）。
好处：计划是显式的，人可以中途介入、可以缓存、可以并行。
坑：计划一旦基于错误假设，后面全错——所以要允许「执行中发现计划错了就重规划」。

## 3. Reflection（反思/自我修正）

让模型检查自己的输出再改一版。常见形式：生成 → 批评 → 修订。

有效场景：写作、代码生成、格式严格的结构化输出。
无效场景：模型没有的新信息时，自我批评只是在原地打转。

## 4. 多 Agent

- **Orchestrator-Worker**：主 Agent 拆任务，子 Agent 各自独立上下文执行，主 Agent 汇总。主要收益是**上下文隔离**，不是「更聪明」。
- **Debate / 多视角**：多个角色给不同意见再裁决。成本高，只在决策类任务上值得。
- **Handoff**：按领域把对话交给专职 Agent（客服分流）。

提醒：多 Agent 的调试成本是单 Agent 的数倍。**先把单 Agent 做到极限，再拆**。

## 5. 什么时候用工作流而不是 Agent

```
模型决定「下一步做什么」   -> Agent
代码决定「下一步做什么」   -> Workflow
```

生产系统里大量场景其实是 Workflow 里嵌几个 Agent 节点，而不是纯 Agent。这样可控、可测、可预算。

## 选型速查

| 任务特征 | 建议 |
|----------|------|
| 步数少、路径不确定 | ReAct |
| 步数多、子任务可并行 | Plan-and-Execute |
| 输出质量要求高、可反复迭代 | Reflection |
| 子任务需要大量独立上下文 | Orchestrator-Worker |
| 步骤固定、合规要求高 | Workflow + Agent 节点 |
