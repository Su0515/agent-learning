# 05 评测与调试

Agent 最难的不是写出来，是**知道它变好还是变差了**。没有评测集，每次改提示词都靠感觉，迟早失控。

## 三层评测

1. **单步评测**：给定上下文，模型是否选了正确的工具、参数对不对。便宜、迭代快，先做这个。
2. **轨迹评测**：整条执行路径是否合理（步数、有没有绕路、有没有重复调用）。
3. **端到端评测**：最终结果对不对。最接近真实价值，但也最贵、最难判定。

## 建评测集的最小做法

```json
[
  {
    "id": "case-001",
    "input": "统计 examples 目录下有多少个 py 文件",
    "expected_tools": ["list_dir"],
    "expected_result": "2",
    "tags": ["tool-use", "easy"]
  }
]
```

从线上真实失败案例里捞 20~50 条就够起步。每条必须能自动判定（精确匹配 / 包含 / 用 LLM 当裁判 / 断言脚本）。

## 关键指标

| 指标 | 说明 |
|------|------|
| 成功率 | 端到端通过率，最重要的单一指标 |
| 平均步数 | 步数暴涨通常意味着模型在试错或循环 |
| 工具错误率 | 参数错误 / 不存在的工具 / 超时 |
| 单任务成本 | token 数 × 单价，直接决定能不能上线 |
| P95 延迟 | 用户体感由长尾决定 |

## 可观测性

每次运行至少要能回答：

- 模型看到了什么（完整 messages）？
- 每一轮为什么这么决策？
- 每个工具的入参、出参、耗时、错误？
- 最终在哪一步终止（正常结束 / 达到 max_steps / 异常）？

做法：以 trace 为单位打日志，一次任务一个 `trace_id`，每轮一个 span。有 LangSmith / Langfuse / Phoenix 这类现成工具，也可以先落地成 JSONL 文件。

## 调优顺序（重要）

按投入产出比排序，不要一上来就换模型：

1. **看失败样本**，归类（工具描述问题 / 缺工具 / 上下文丢信息 / 模型能力不足）
2. **改工具描述和返回值**——大多数问题在这里
3. **改提示词**，把约束写死、给正反例
4. **加/换工具**，补齐能力缺口
5. **加反思或重试**
6. 最后才考虑换更强的模型

## 踩坑记录

- 只测 happy path：长尾任务才是 Agent 的价值所在，也是失败集中地。
- 评测集和提示词一起改：等于既当运动员又当裁判，分数没有意义。
- 用 LLM 当裁判但不校准：跟人工标注对 20 条，确认判定标准一致。

## 动手练习

1. 给 `minimal_agent.py` 写 5 条评测用例和一个跑批脚本，输出成功率与平均步数。
2. 把失败用例的 trace 存成 JSONL，训练自己从日志里定位问题。
