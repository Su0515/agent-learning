# 03 记忆与上下文

上下文窗口是 Agent 最稀缺的资源。所有「记忆」问题本质都是：**什么该进上下文，什么该留在外面**。

## 四层记忆

| 层 | 存什么 | 生命周期 | 实现 |
|----|--------|----------|------|
| 工作记忆 | 本轮消息历史、工具结果 | 单次任务 | messages 数组 |
| 会话记忆 | 用户偏好、已确认结论 | 一次会话 | 摘要后放 system |
| 长期记忆 | 跨会话的事实、经验 | 持久 | 数据库 / 文件 + 检索 |
| 外部知识 | 文档、代码库 | 持久 | RAG / 搜索工具 |

新手最常见的错误：只做第一层，然后任务一长就崩。

## 上下文膨胀的四种解法

1. **截断（Truncate）**：只保留最近 N 轮。简单，但会丢掉早期关键信息。
2. **摘要（Summarize）**：超过阈值时把旧消息压成一段摘要。要保留：目标、已完成的步骤、关键结论、未解决的问题。
3. **卸载（Offload）**：大块结果（网页正文、长文件）只留路径/ID 在上下文里，需要时再读回来。这是最有效的做法。
4. **检索（Retrieve）**：长期记忆按相关性检索注入，而不是全量塞进去。

实用组合：**卸载 + 摘要**。工具返回只留摘要和引用 ID，历史超阈值时压缩。

## 为什么大模型会「忘事」

不是模型记性差，而是：
- 关键信息被后来的长内容稀释（lost in the middle）；
- 早期确立的目标/约束被摘要丢了；
- 工具结果被截断成一半的句子。

对策：把**目标和约束**放在 system 或每轮重新注入，别指望它一直记得。

## 记忆写入要有节制

长期记忆不是越多越好：
- 写入前判断「这条信息半年后还有用吗」；
- 记忆要有来源和时间戳，否则会被过期事实误导；
- 提供「遗忘/纠错」通道，让用户可以删。

## 踩坑记录

- 摘要只压历史、忘了压工具结果 → 上下文还是爆。
- 把 RAG 检索结果整段塞进去 → 一次注入 5 万字，成本失控。
- 记忆没有命名空间 → 不同项目的偏好互相污染。

## 动手练习

1. 在示例中给消息历史加一个「超过 20 条就摘要旧消息」的逻辑。
2. 把工具返回改成「摘要 + 文件路径」双段式，观察轮数和 token 变化。
